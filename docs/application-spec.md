# アプリケーション仕様書 — 商品在庫管理システム

本書は、TDD 検証の題材となる「商品在庫管理システム」の仕様を定義する。
TDD 検証が主目的のため、**テストケース設計** を最重要視する。各機能には一意の ID を振り、テストケースと対応づけてダッシュボードで進捗を可視化する。

---

## 1. システム概要

社内で扱う商品マスタと在庫を管理する最小限の業務アプリケーション。

- アクター: 在庫管理担当者（単一ロール。本検証では認証・認可は最小限／スコープ外とする）
- 構成: フロントエンド（Vue）→ REST API（Spring Boot）→ DB（SQL Server）

### 用語

| 用語 | 説明 |
| --- | --- |
| 商品 (Product) | 在庫管理の対象となるマスタ。商品コードで一意。 |
| カテゴリ (Category) | 商品の分類。 |
| 在庫 (Stock) | 商品ごとの現在数量。 |
| 入出庫 (Stock Transaction) | 在庫を増減させる取引（入庫=IN / 出庫=OUT）。 |

## 2. データモデル（論理）

> 物理名は SQL Server 向け。命名・型は [SQL コーディング規約](./coding-standards/sql-coding-standards.md) に準拠する。

### 2.1 category（カテゴリ）

| 物理名 | 論理名 | 型 | 制約 |
| --- | --- | --- | --- |
| category_id | カテゴリID | INT | PK, IDENTITY |
| category_name | カテゴリ名 | NVARCHAR(50) | NOT NULL, UNIQUE |
| created_at | 作成日時 | DATETIME2 | NOT NULL |
| updated_at | 更新日時 | DATETIME2 | NOT NULL |

### 2.2 product（商品）

| 物理名 | 論理名 | 型 | 制約 |
| --- | --- | --- | --- |
| product_id | 商品ID | INT | PK, IDENTITY |
| product_code | 商品コード | VARCHAR(20) | NOT NULL, UNIQUE |
| product_name | 商品名 | NVARCHAR(100) | NOT NULL |
| category_id | カテゴリID | INT | NOT NULL, FK(category) |
| unit_price | 単価 | DECIMAL(12,2) | NOT NULL, >= 0 |
| status | ステータス | VARCHAR(10) | NOT NULL（ACTIVE / INACTIVE） |
| description | 説明 | NVARCHAR(500) | NULL 可 |
| deleted_flag | 削除フラグ | BIT | NOT NULL, 既定 0 |
| version | 排他制御用バージョン | INT | NOT NULL, 既定 0 |
| created_at | 作成日時 | DATETIME2 | NOT NULL |
| updated_at | 更新日時 | DATETIME2 | NOT NULL |

### 2.3 stock（在庫）

| 物理名 | 論理名 | 型 | 制約 |
| --- | --- | --- | --- |
| product_id | 商品ID | INT | PK, FK(product) |
| quantity | 在庫数量 | INT | NOT NULL, >= 0 |
| updated_at | 更新日時 | DATETIME2 | NOT NULL |

### 2.4 stock_transaction（入出庫履歴）

| 物理名 | 論理名 | 型 | 制約 |
| --- | --- | --- | --- |
| transaction_id | 取引ID | BIGINT | PK, IDENTITY |
| product_id | 商品ID | INT | NOT NULL, FK(product) |
| transaction_type | 取引区分 | VARCHAR(3) | NOT NULL（IN / OUT） |
| quantity | 数量 | INT | NOT NULL, > 0 |
| transaction_at | 取引日時 | DATETIME2 | NOT NULL |
| note | 備考 | NVARCHAR(200) | NULL 可 |

## 4. 機能一覧（ダッシュボード追跡対象）

各機能 ID はダッシュボードの行になる。1 機能 = 複数テストケース。

| 機能ID | 機能名 | 対応画面 | 概要 |
| --- | --- | --- | --- |
| F-01 | 商品検索 | SC-01 | コード/商品名/カテゴリ/ステータスで検索、ページング・ソート。 |
| F-02 | 商品詳細取得 | SC-02 | 商品IDで1件取得。 |
| F-03 | 商品登録 | SC-02 | 入力検証のうえ新規登録。在庫0で初期化。 |
| F-04 | 商品更新 | SC-02 | 入力検証＋楽観ロックで更新。 |
| F-05 | 商品削除 | SC-02 | 論理削除（在庫がある場合は不可）。 |
| F-06 | カテゴリ一覧取得 | SC-01/02 | カテゴリの一覧を取得。 |
| F-07 | 在庫照会 | SC-03 | 商品ごとの在庫数量を取得。 |
| F-08 | 入庫登録 | SC-04 | 在庫数量を加算し履歴を記録。 |
| F-09 | 出庫登録 | SC-04 | 在庫数量を減算（不足チェック）し履歴を記録。 |
| F-10 | 入出庫履歴照会 | SC-05 | 商品の入出庫履歴を時系列で取得。 |

## 5. API 仕様（概略）

| 機能ID | メソッド | パス | 概要 |
| --- | --- | --- | --- |
| F-01 | GET | `/api/products?code=&name=&categoryId=&status=&page=&size=&sort=` | 商品検索 |
| F-02 | GET | `/api/products/{id}` | 商品詳細 |
| F-03 | POST | `/api/products` | 商品登録 |
| F-04 | PUT | `/api/products/{id}` | 商品更新（body に version） |
| F-05 | DELETE | `/api/products/{id}` | 商品論理削除 |
| F-06 | GET | `/api/categories` | カテゴリ一覧 |
| F-07 | GET | `/api/products/{id}/stock` | 在庫照会 |
| F-08 | POST | `/api/products/{id}/stock/in` | 入庫 |
| F-09 | POST | `/api/products/{id}/stock/out` | 出庫 |
| F-10 | GET | `/api/products/{id}/stock/transactions` | 入出庫履歴 |

### 入力検証ルール（主なもの）

- product_code: 必須、半角英数字、1〜20 文字、ユニーク。
- product_name: 必須、1〜100 文字。
- category_id: 必須、存在するカテゴリ。
- unit_price: 必須、0 以上、小数 2 桁まで。
- status: `ACTIVE` または `INACTIVE`。
- 入出庫 quantity: 必須、1 以上の整数。
- 出庫: `現在在庫 - quantity >= 0` を満たすこと。

### エラー応答（共通）

| HTTP | 用途 |
| --- | --- |
| 400 | 入力検証エラー（フィールド別メッセージを返す） |
| 404 | 対象リソースなし |
| 409 | 楽観ロック競合 / 業務制約違反（在庫不足・在庫保持中の削除など） |

## 6. テストケース設計

> 本リポジトリの核。各機能に対し、レイヤ別のテストケースを定義する。TDD では **これらを先に実装し、全件 FAIL（RED）から開始** する。
>
> テストケース ID 体系: `<機能ID>-<レイヤ>-<連番>`
> レイヤ: `UT`=バックエンド単体 / `IT`=バックエンド結合(API+DB) / `FE`=フロント単体 / `E2E`=E2E

### 6.1 F-01 商品検索

| テストID | レイヤ | 観点 | 期待結果 |
| --- | --- | --- | --- |
| F-01-UT-01 | UT | 商品名の部分一致検索 | 該当商品のみ返る |
| F-01-UT-02 | UT | カテゴリ＋ステータス複合条件 | AND 条件で絞り込まれる |
| F-01-UT-03 | UT | 論理削除済みは除外 | deleted_flag=1 は返らない |
| F-01-UT-04 | UT | ソート指定（単価昇順/降順） | 指定順に並ぶ |
| F-01-IT-01 | IT | 検索 API 200・ページング | totalCount / page 情報が正しい |
| F-01-IT-02 | IT | 条件なし検索 | 全件（削除除く）が返る |
| F-01-FE-01 | FE | 検索フォーム入力→一覧描画 | 結果行が描画される |
| F-01-FE-02 | FE | 0 件時の空表示 | 「該当データなし」を表示 |

## 7. ダッシュボード仕様（進捗可視化）

- 入力: 各テストランナーの結果
  - バックエンド: Surefire/Failsafe の JUnit XML
  - フロント: Vitest の JSON レポート
  - E2E: Playwright の JSON レポート
- 集計: `scripts/aggregate-test-results.*` が、テストID（`F-xx-...`）を機能 IDにマッピングし、機能ごとに `total / passed / failed / skipped` を持つ `test-results.json` を生成する（決定論的スクリプト）。
- 表示: `dashboard/` が `test-results.json` を読み込み、機能一覧（行）× テストケース状況（PASS/FAIL/未実装）をひと目で表示する。

> テスト名に機能ID（`F-01-UT-01` 等）を含める規約とし、集計を機械的に行えるようにする（揺らぎ排除）。

## 8. スコープ外（本検証では扱わない）

- 認証・認可、複数ロール、監査ログ
- 多言語対応、アクセシビリティの厳密対応
- 複雑な在庫評価（先入先出など）
- 帳票出力
