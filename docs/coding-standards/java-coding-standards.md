# Java コーディング規約（コンテキスト用要約）

> 本書は [Future 社 Java コーディング規約](https://future-architect.github.io/coding-standards/documents/forJava/Java%E3%82%B3%E3%83%BC%E3%83%87%E3%82%A3%E3%83%B3%E3%82%B0%E8%A6%8F%E7%B4%84.html)（CC-BY-4.0）を、AI / 開発者が作業時に参照しやすいよう要約・再構成したものです。詳細・最新は原典を参照してください。Spring Boot バックエンド実装はこの規約に準拠します。

## 5 つの原則
1. **可読性を最優先**: 人が読んで理解できるコードを書く。
2. **明確な命名**: 曖昧でない、意味の伝わる名前を使う。
3. **由来を理解する**: サンプルを盲目的にコピーしない。
4. **重複を避ける**: 共通処理は再利用可能なメソッドへ。
5. **単一責務**: メソッド/クラスは 1 つの役割に絞る。

## 1. 命名規約
- 大文字小文字の違いだけで区別する名前を避ける。意味が伝わる名前を使う。
- **パッケージ**: すべて小文字。
- **クラス/インタフェース/enum/record**: PascalCase。
- **メソッド**: camelCase。getter は `get`＋属性名、boolean は `is`＋属性名、setter は `set`＋属性名、変換は `to`＋対象名（例: `toString()`）。boolean を返すメソッドは真偽が明確な名前にする（`isAsleep()`, `exists()`, `hasExpired()`）。
- **変数**: camelCase。boolean 変数は真偽が明確な名前に（汎用的な `flag` は避ける）。
- **定数**: `static final`、`ALL_CAPS`（単語間アンダースコア）。プリミティブまたは不変オブジェクトのみ。
- **enum 定数**: `ALL_CAPS`。
- パラメータ名にインスタンス変数名と同名を使わない（IDE 自動生成のアクセサ/コンストラクタは例外）。区別目的のアンダースコア `_` は使わない。
- ループカウンタは `i`, `j`, `k`（ネスト順）。

## 2. フォーマット
- インデントは **半角スペース 4**（タブ不可）。
- 1 行 1 文。極端に長い行を避ける。
- 開き波括弧 `{` は同じ行に置き、`{` の後に文を書かない。
- 演算子・カンマの後にスペース。代入/論理/関係/算術/ビット演算子は前後にスペース。`++`/`--` は被演算子と空白を空けない。
- `if` / `while` / `for` / `do-while` は単文でも必ず波括弧を付ける。
- 条件式内で代入（`=`）しない。空ブロック `{}` を避ける。
- 範囲比較は不等号を左向きに揃える: `from <= x && x <= to`。

## 3. コメント
- **Javadoc** (`/** */`): クラスは `@author`/`@version`、メソッドは `@param`/`@return`/`@exception`。オーバーライドは `{@inheritDoc}`、サンプルは `{@snippet}`。
- 「何を」ではなく「なぜ」を書く（コードが「何を」を語る）。冗長な言い換えコメントを避ける。
- コメントアウトされたコードは残さず、バージョン管理に委ねる。
- TODO 形式: `//TODO: 説明 [関連チケット#]`。

## 4. 一般的なコーディング
- 適切な可視性で宣言する。**インスタンス変数は `private`**。実装クラスよりインタフェース参照を優先。
- `final` を活用（継承不可クラス、オーバーライド不可メソッド、不変値）。メソッド引数は原則 `final`、再代入しない。
- **null の扱い**: null を返すより空コレクション/空配列を返す。`equals()` は左辺が null にならないように。任意値は `Optional` で表現。
- メンバ順序: static フィールド → static 初期化子 → static メソッド → インスタンスフィールド → 初期化子 → コンストラクタ → インスタンスメソッド。各区分内は `public`→`protected`→package-private→`private`。

## 5. 配列・コレクション
- 配列は `type[]` 形式で宣言。ジェネリクスは `List<String> list = new ArrayList<>();`。
- 不変コレクションは `List.of()` / `Set.of()` / `Map.of()`。可変配列を public 定数として公開しない。配列コピーは `Arrays.copyOf()`。
- `Vector` / `Hashtable` / `Enumeration` を使わない。`List.sort()` を使う（`Collections.sort()` ではなく）。
- 全要素走査は拡張 for 文を優先（`Collection.forEach()` を List/Set で多用しない）。
- 先頭/末尾操作が多い大規模コレクションは `LinkedList` / `ArrayDeque` を検討。

## 6. 文字列
- 比較は `equals()`（`==` 不可）。`new String()` で生成しない。
- 可変文字列は `StringBuilder`、スレッドセーフが必要なら `StringBuffer`。1 文での連結は `+`。
- 日付整形は `DateTimeFormatter`（または `SimpleDateFormat`）。プリミティブ→文字列は `String.valueOf()`。`BigDecimal`→文字列は `toPlainString()`。
- 複数行は text block（Java 13+）を優先。システム依存記号（`\n` 等）の直書きを避ける。

## 7. 数値
- 金額など正確な計算は `BigDecimal`。比較は `compareTo()`（`equals()` は精度に厳密）。符号判定は `signum()`。
- 精度が落ちる型へのキャストを避ける。instanceof はパターンマッチング: `if (o instanceof String s)`。

## 8. 制御フロー
- 単一値の代入は switch 式。アロー構文（`->`）でフォールスルー回避。enum を網羅する switch 式では `default` 省略可。
- 連鎖する `instanceof` より switch パターンマッチング。sealed 型で網羅性チェック。
- 拡張 for で全件走査。ループ変数を書き換えない。
- 三項演算子のネストは禁止。

## 9. ラムダ / 関数型 / Stream
- ラムダは匿名クラスより優先。型宣言は省略、単一式に留め複数行は別メソッド化。可能ならメソッド参照を優先。
- **Stream**: 並列ストリームは使わない。中間操作は最大 3 つ目安。各操作の `.` の前で改行。Stream を変数に代入しない（単一利用）。
- **Optional**: 単一利用なら変数代入しない。終端操作で速やかに値を取り出す。

## 10. var（型推論）
プロジェクトで方針を 1 つに統一する（不使用／全面使用／右辺型が明確な場合のみ）。スタイル混在を避ける。

## 11. record / sealed / text block
- **record**: 使用前にガイドラインを定め、JavaBeans と混在させない（互換性に注意）。
- **sealed**: 使用範囲をプロジェクトで明示（内部ライブラリ限定／特定レイヤ／禁止 等）。
- **text block**: 複数行文字列に使用。単一行には使わない。

## 12. 継承・ポリモーフィズム
- オーバーライドには必ず `@Override`。スーパークラスの private をオーバーライドしない。インスタンス変数を再宣言しない。

## 13. 例外処理
- 具体的な例外型を catch（`Exception` を直接 catch / throw しない）。ログには例外詳細を含める（`log.error("...", e)`）。
- 空結果は null でなく空コレクション/配列。リソースは try-with-resources。
- `finalize()` をオーバーライド/明示呼び出ししない。

## 14. 設計原則
- 単一責務（テスト容易性・保守性）。不変性を優先。変数は使用直前に宣言し、用途を使い回さない。ローカル変数をインスタンス変数より優先。

## 15. パフォーマンス
- 反復連結は `StringBuilder`。大規模データでは拡張 for が有利。`ArrayList` はランダムアクセス向き、`LinkedList` は先頭/末尾操作向き。ラムダ/メソッド参照は匿名クラスより効率的。

## 本プロジェクトでの適用メモ
- Spring Boot のレイヤ（Controller / Service / Repository）で単一責務を徹底する。
- DTO・ドメインの不変性を意識し、検証は Bean Validation を基本とする。
- テストメソッド名には機能ID（例 `F_03_UT_01_正常登録`）を含め、ダッシュボード集計と対応づける（[application-spec.md](../application-spec.md#7-ダッシュボード仕様進捗可視化) 参照）。
